Lesson 7 · Capstone

Put it together: trace both journeys, then break things

No new facts. This is the test of whether it stuck — reconstruct from memory, then diagnose.

Where this sits → Your mission was to understand this architecture well enough to draw it from memory and trace a request through it. That's literally this lesson. Everything is on the blueprint — but try hard to answer before you peek.
How to do this lesson For each prompt below, say the answer out loud or write it down first, then expand to check. The effort of retrieving — even when you're not sure — is what converts fluency into durable memory. Peeking first feels easier and teaches you almost nothing.

Part A · The user's journey, from a blank page

A user types your app's URL. Name every hop the request takes, in order, and one word on each hop's role.

Reveal the user path (①→②)
  1. Internet Gateway — the one door into the VPC (Lesson 2).
  2. Application Load Balancer — public front door in the public subnets; the only thing with a public DNS name (Lesson 4).
  3. Listener → target group — the ALB forwards to a pool of healthy servers (Lesson 4).
  4. EC2 app server — in a private subnet, no public IP, reached over the local route (Lessons 1 & 3).
  5. The response returns back out the same chain. No server ever had a public IP.
Reveal: which security-group rules made that path legal, and no other?
ALB's SG: allow 443 from 0.0.0.0/0 (the internet). App server's SG: allow the app port from the ALB's security group — not an IP range, so it survives scaling. Anything that skips the ALB matches no rule and is dropped (Lesson 5).

Part B · Your journey, from a blank page

Now you need to SSH into 10.0.11.5 to check a log. It has no public IP and its SG only trusts the ALB. Walk the path — and don't forget the gotcha.

Reveal the admin path (Ⓐ→Ⓑ)
  1. Your laptop's OpenVPN client connects to the Client VPN endpoint and authenticates (Lesson 6).
  2. You're handed a private address from the client CIDR range — your laptop is now inside the VPC's world.
  3. You reach 10.0.11.5 directly over the local route — the same one internal resources use (Lesson 2).
  4. The gotcha: the server's security group must still allow port 22 from the VPN. Being on the network isn't permission (Lesson 5).
Reveal: why not just use a bastion host or give the server a public IP?
A public IP throws away the private design entirely. A bastion works but is a permanent internet-facing machine you must patch and defend. Client VPN gives you inside-the-network access with no public jump box to run (Lesson 6).

Part C · Spot the broken config

Real understanding shows up in diagnosis. Each scenario has one root cause — pick it from memory.

D1. Users get timeouts. The ALB is up, but every target shows unhealthy. Root cause?
Correct. Health checks fail because the app server's security group doesn't allow the app port from the ALB's SG, so the ALB can't even reach it. (NAT is about outbound; VPN is the admin path — neither is in the user flow.)
The ALB can't reach the targets: the server's security group isn't allowing the app port from the ALB's SG (Lesson 5). NAT and VPN aren't part of the user request path.
D2. Users load the site fine, but the app server's apt update hangs forever. Root cause?
Correct. Inbound (via ALB) works, but outbound needs 0.0.0.0/0 → NAT in the private route table (Lesson 3). A public IP is exactly what we avoid — the NAT is the outbound answer.
Inbound works; outbound is broken. The private subnet needs 0.0.0.0/0 → NAT (Lesson 3). We deliberately give the server no public IP — the NAT handles egress.
D3. Your VPN connects successfully, but ssh 10.0.11.5 just times out. Root cause?
Correct. You're on the network, but the server's security group still gates the port — add allow-22-from-VPN (Lessons 5 & 6). An overlapping CIDR would usually block the connection from working at all, not just SSH.
Being connected isn't permission — the server's security group must allow port 22 from the VPN (Lessons 5 & 6). The IGW isn't involved in this private, inside-the-VPC path.
D4. The internet can't reach your ALB at all — its DNS name just times out. Likeliest root cause?
Correct. An internet-facing ALB must live in public subnets (0.0.0.0/0 → IGW). Placed in private subnets, nothing from outside can reach it (Lessons 2 & 4).
An internet-facing ALB must sit in public subnets with a route to the IGW (Lessons 2 & 4). Unhealthy targets or NAT throughput wouldn't make the ALB itself unreachable.

Part D · Draw the whole thing from memory

Final challenge. On a blank page, sketch the full architecture — then check yourself against this list. If you can produce ten of these twelve with their one-line role, your mission is met.

Reveal the twelve boxes to check against
VPC (private network, a CIDR) · 2 Availability Zones (survive one datacenter failing) · public subnets (route to IGW) · private subnets (no route to IGW) · route tables (what makes each subnet public or private) · Internet Gateway (the door) · NAT Gateway (outbound-only valve) · Application Load Balancer (public front door) · EC2 app servers (private, no public IP) · Security Groups (per-resource, stateful firewall) · Client VPN (your way inside) · and the two journeys that connect them. Full picture: the blueprint.
Bonus recall · which four things bill while idle? NAT Gateway (per hour + per GB), ALB (per hour + LCU), Client VPN (per association-hour + per connection-hour), and each public IPv4 address. The VPC, subnets, route tables, IGW, and security groups themselves are free to define.
