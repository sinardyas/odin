Lesson 5 · The firewall layer

Security Groups (and their subnet-level cousin)

Routing decides where traffic can go. Security groups decide who's actually allowed to talk.

Where this sits → Lessons 1–4 built the plumbing: a request can travel internet → ALB → app server. But "can travel" isn't "is permitted." This lesson adds the Security Group boxes from the blueprint — the per-resource firewall that makes the design tight instead of merely functional.

1. Routing ≠ permission

A route table answers "which door does traffic bound for X leave through?" It never asks "should this sender be talking to this receiver at all?" Without a firewall, anything that can route to your app server — every other resource in the VPC — could knock on its door. We want exactly one thing to be allowed in: the load balancer.

2. A Security Group is a stateful, allow-only firewall around a resource

A Security Group (SG) wraps an individual resource (an instance, the ALB, etc.) with two short lists: inbound rules and outbound rules. Three properties define how it behaves:[aws]

Allow-only
You can only write "allow" rules. There's no "deny." If no rule permits a packet, it's dropped by default.
Stateful
If you allow a request in, its reply is automatically allowed back out — you never write return rules. This is the big one, and the sharpest contrast with NACLs below.
Per-resource
It attaches to the resource itself, not the subnet. Two servers in the same subnet can have completely different security groups.

3. The trick: a rule can name another security group

This is the feature that completes Lesson 4. A security-group rule's source doesn't have to be an IP range — it can be another security group. So the app server's rule reads, literally, "allow inbound on my app port from whatever is in the load balancer's security group" — no IP addresses, no matter how many servers scale up or down.[aws]

Chain them and the whole path becomes a series of "who may talk to whom" statements:

Security group on…Inbound ruleIn plain words
the ALBHTTPS:443 from 0.0.0.0/0"The whole internet may reach me on 443."
the app serverapp port from ALB's SG"Only the load balancer may reach me — no one else."
Now the design is actually tight Even though the app server sits in a routable VPC, the only traffic it accepts comes from the ALB. A compromised neighbour in the same subnet still can't open a connection to it. Routing made the path possible; the security group made it exclusive.

4. The other firewall: Network ACLs (know it exists)

There's a second, subnet-level firewall called a Network ACL (NACL). You'll rarely touch it — most designs leave it at its default "allow everything" and do the real work in security groups — but you should know how it differs, because AWS puts them side by side:[aws]

Security GroupNetwork ACL
Wrapsa resource (instance/ALB)a whole subnet
Rulesallow onlyallow and deny
Statestateful (replies auto-allowed)stateless (must allow both directions)
You'll use itconstantly — the main toolrarely — usually left at default

Rule of thumb: reach for security groups first. Only drop to NACLs when you need a blunt, subnet-wide deny (e.g. block a bad IP range) — something SGs, being allow-only, can't express.

Check yourself

From memory — mixing in Lessons 2 and 4.

Q1. What does "stateful" mean for a security group?
Correct. If inbound is allowed, the matching response is allowed back out without a separate rule. NACLs, being stateless, need both directions written explicitly.
Stateful means the reply to an allowed request returns automatically — no return rule needed. (The subnet-wide, both-directions one is the NACL.)
Q2. How does the app server's rule best express "only the load balancer may reach me"?
Correct. Naming the ALB's security group as the source needs no IPs and survives servers scaling in and out. Security groups are allow-only, so there's no "deny," and routing isn't permission.
You name the ALB's security group as the allowed source. Security groups can't "deny" (allow-only), and route tables decide paths, not permission.
Q3. You must block one specific bad IP range across a whole subnet. Which tool fits?
Correct. Security groups are allow-only, so they can't express "deny this range." A NACL is stateless, subnet-wide, and supports deny rules — the right tool for a blunt block.
Security groups can't deny (allow-only). A NACL is the subnet-wide firewall that supports deny rules — the right fit for blocking a range.
