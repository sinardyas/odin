Lesson 3 · Outbound without exposure

The NAT Gateway: a one-way valve

How a server with no way in still reaches out to the world — and why that's not a contradiction.

Where this sits → Lesson 2 ended with a private subnet that has no route to the internet. Good for security — but your app servers still need to download OS patches, pull packages, and call external APIs. This lesson fills the NAT Gateway box in the blueprint that resolves the tension.

1. The problem we backed ourselves into

A private-subnet server is deliberately unreachable from the internet — that's the whole design. But "unreachable" cuts both ways: with only the local route, it also can't reach out to run apt update or hit a payment API. We need outbound internet without inbound exposure.

The obvious fix — add 0.0.0.0/0 → igw like a public subnet — is wrong here, for two reasons:

  • An Internet Gateway only works for resources that have a public IP. Our servers have none.
  • Even if we gave them one, that door swings both ways — the internet could now start connections in. Exactly what we're avoiding.

2. The NAT Gateway: outbound-only by design

A NAT Gateway is a managed one-way valve. It lives in a public subnet and does one job: when a private server sends traffic to the internet, the NAT swaps the server's private source address for its own, forwards the request out through the Internet Gateway, and relays the reply back.[aws]

The asymmetry is the point: because every conversation must be started from inside, nothing on the internet can use the NAT to open a connection to your servers. Outbound: yes. Inbound: impossible.

The mental model An Internet Gateway is a two-way door (needs a public IP, allows inbound). A NAT Gateway is a one-way valve (no public IP on the server, outbound only). Same internet, opposite exposure.

3. It's still just one line in a route table

Here's the satisfying part — you already know how this is wired. The private subnet's route table gets the same catch-all line from Lesson 2, pointed at a different target:

DestinationTargetSubnet type
10.0.0.0/16localboth
0.0.0.0/0igw-…public — traffic goes straight out
0.0.0.0/0nat-…private — traffic goes out via the valve

Public subnet: catch-all → Internet Gateway. Private subnet: catch-all → NAT Gateway. Same 0.0.0.0/0 you met in Lesson 2 — the target is what changes the behaviour.[aws]

Cost radar — this one actually meters Unlike the Internet Gateway (free), a NAT Gateway bills two ways at once: roughly $0.045 per hour it exists plus ~$0.045 per GB of data it processes.[aws] Running one per AZ for high availability (the blueprint's shape) doubles the hourly charge. It's often the first "why is my VPC costing money?" line item — worth remembering before you build.

Check yourself

From memory — and we're deliberately mixing Lesson 2's route table back in.

Q1. What is the defining property of a NAT Gateway?
Correct. Connections must start from inside; the NAT relays them out and returns replies, but nothing outside can use it to initiate a connection in.
It's the one-way valve: outbound connections yes, inbound starts no. It doesn't give servers public IPs, and it still relies on the IGW to actually egress.
Q2. In the private subnet's route table, where does the 0.0.0.0/0 route point?
Correct. Same catch-all line as Lesson 2, but the target is the NAT Gateway, not the IGW. The changed target is what makes it outbound-only.
It points to the NAT Gateway. It's the same 0.0.0.0/0 catch-all from Lesson 2 — only the target differs (NAT, not IGW), which is what enables safe outbound.
Q3. Which subnet does the NAT Gateway itself live in, and why?
Correct. The NAT needs its own route out, so it sits in a public subnet (with the 0.0.0.0/0 → IGW route). Private servers then point at the NAT.
It lives in a public subnet — it needs the 0.0.0.0/0 → IGW route to actually egress. Private servers route to the NAT; the NAT routes to the IGW.
