Lesson 4 · The public front door

The Application Load Balancer

How the internet reaches your app while every server stays private — the payoff the whole course is named after.

Where this sits → Your app servers are private: no public IP, no inbound route (Lessons 2–3). So how does a user ever load the app? This lesson fills the Application Load Balancer box in the blueprint — the one public thing that lets the private things stay private.

1. The front-door trick

Remember the three conditions for internet reachability from Lesson 2: an IGW attached, a 0.0.0.0/0 → igw route, and a public IP. Your app servers deliberately fail the third. So instead of exposing them, you put one resource in the public subnets that satisfies all three, and let it speak to the servers on the internet's behalf. That resource is the Application Load Balancer (ALB).[aws]

The user only ever talks to the ALB. The ALB — sitting inside your VPC — turns around and forwards the request to a private server over the local route. The internet never sees the server; it sees the load balancer's public DNS name and nothing else.

Why "load balancer," not just "gateway"? It also spreads incoming requests across many app servers, so no single one is overwhelmed — and it works at Layer 7, meaning it understands HTTP and can route by URL path or hostname (e.g. /api to one pool, / to another).[aws]

2. Three words that describe every ALB

Listener
What the ALB accepts at the front: a protocol + port, like HTTP:80 or HTTPS:443. "I'm listening for web requests here."
Target group
The pool of destinations behind it — your private EC2 app servers. The listener forwards matching requests to a target group.
Health check
The ALB pings each target on a path (say /health) and only sends traffic to the ones that answer. A crashed server is quietly skipped.[aws]

Read it as a sentence: a listener on HTTPS:443 forwards requests to a target group of app servers, skipping any that fail their health check. That single line is 90% of an ALB.

3. Spanning both AZs — the HA reflex returns

You place the ALB across both public subnets (one per Availability Zone, from Lesson 1). It then balances across app servers in both private subnets. If AZ A's datacenter fails, the ALB simply stops sending there and keeps serving from AZ B. The multi-AZ shape you set up in Lesson 1 is what makes this resilience automatic.

4. Trace the whole path (this is the win)

You now know every hop. Follow a single HTTP request from a user's browser to your code:

Browser
  → Internet Gateway        (the door into the VPC — Lesson 2)
  → Application Load Balancer  (public subnet, has the public DNS — this lesson)
  → target group            (listener forwards to healthy servers)
  → EC2 app server          (private subnet, no public IP — Lessons 1 & 3)
  → your app responds, back out the same way

Nowhere in that chain did a server need a public IP. That is "serve an app to the internet from a private network."

Cost radar An ALB bills per hour it runs plus per LCU (a bundled unit of connections, bandwidth, and rules used).[aws] Smaller than a NAT bill for light traffic, but it's another always-on meter — one ALB usually fronts many servers, so you run one, not one-per-server.

Check yourself

From memory — pulling Lessons 1–3 back in on purpose.

Q1. How does a user reach an app server that has no public IP?
Correct. The ALB is the only public-facing piece; it accepts the request and forwards it to a private server over the VPC's local route. The server stays private.
The ALB is the public front door — it receives the request and forwards it inward. Servers never get a public IP, and NAT is outbound-only (Lesson 3).
Q2. What does an ALB's health check accomplish?
Correct. The ALB probes each target and quietly skips any that fail, so users aren't sent to a crashed server.
Health checks let the ALB send traffic only to targets that respond, skipping unhealthy ones. They don't assign IPs or act as the firewall.
Q3. Which subnets does the internet-facing ALB itself sit in?
Correct. To be the public front door it must be reachable — so it lives in the public subnets (with the IGW route), one per AZ. It then forwards to private targets.
An internet-facing ALB sits in the public subnets so the internet can reach it; from there it forwards to the private app servers.
