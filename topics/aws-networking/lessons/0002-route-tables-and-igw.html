Lesson 2 · What makes a subnet public

Route tables & the Internet Gateway

The promise from Lesson 1, paid off: we open the route table and watch one line turn a subnet public.

Where this sits → In Lesson 1 you learned a subnet is public or private because of routing, not a name. This lesson shows the exact mechanism — the two boxes in the blueprint that connect your VPC to the internet.

1. A route table is a list of "to reach X, go to Y" rules

Every subnet is associated with exactly one route table: a short list of rules. Each rule has a destination (a CIDR range — remember those from Lesson 1) and a target (where to send traffic headed there).[aws] When traffic leaves a resource, AWS scans the table for the most specific matching destination and sends it to that target.

Here is the route table of a private subnet — the simplest possible one:

DestinationTargetMeans
10.0.0.0/16local"Anything inside my own VPC — I already know how to reach it."

That single local route is added automatically and can never be removed. It's why any two resources in the same VPC can already talk to each other. And because that's the only rule, traffic headed anywhere else — the open internet — has nowhere to go. That is precisely what makes this subnet private.[aws]

2. One extra line makes it public

Now the public subnet's route table. It has the same local route, plus one more:

DestinationTargetMeans
10.0.0.0/16local"Inside my VPC — reach it directly." (same as before)
0.0.0.0/0igw-…"Everywhere else → send to the Internet Gateway."

0.0.0.0/0 is CIDR for "every address that exists" — the catch-all. It's the least specific match, so it only wins when nothing else fits, i.e. for internet-bound traffic. Point that catch-all at an Internet Gateway and the subnet becomes public.[aws]

This is the whole secret Public subnet and private subnet can be identical in every way except this one line. Add 0.0.0.0/0 → igw and it's public; remove it and it's private. Same land, different door policy.

3. The Internet Gateway is the door (and it needs three things)

An Internet Gateway (IGW) is the single, highly-available doorway between your VPC and the public internet. But attaching one isn't enough on its own. For a resource to actually be reachable from the internet, all three must be true:[aws]

  1. An IGW is attached to the VPC.
  2. The subnet's route table sends 0.0.0.0/0 to that IGW. (the line above)
  3. The resource has a public IP address.
Tie it back to the mission In our design the app servers deliberately fail test #3 — they have no public IP and sit in a private subnet. That's the point: the internet can't reach them directly. The public-facing Load Balancer (Lesson 4) is the only thing that satisfies all three — it's the front door, so the servers don't have to be.

Q1. What does the route 0.0.0.0/0 represent in a route table?
Correct. /0 fixes zero bits, so it matches every address. As the least-specific route it only wins for traffic not headed inside the VPC.
/0 fixes zero bits, so it matches every possible address — the catch-all. It's how "send the internet-bound stuff to the gateway" is written.
Q2. Two subnets are identical except their route tables. What makes one public?
Correct — the presence of the 0.0.0.0/0 → Internet Gateway route is the entire difference. Remove it and the same subnet becomes private.
It's the 0.0.0.0/0 → Internet Gateway route. Size and AZ don't decide public vs private — routing does.
Q3. Your app server is in a public subnet but still unreachable from the internet. Likeliest missing piece?
Correct. Reachability needs all three: IGW attached, a 0.0.0.0/0 route to it, AND a public IP on the resource. In a public subnet with the route present, the missing public IP is the usual culprit.
All three conditions must hold: IGW attached, the 0.0.0.0/0 route present, and a public IP on the resource. In a public subnet, the missing public IP is the usual culprit.
